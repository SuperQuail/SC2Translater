# 文件访问与翻译键改造计划（非前端部分）

> 状态：**主体已实现**（2026-10-09）。本文档同时是设计说明与实现记录。
>
> 已落地：文件类型判定 / 同名 JSON 关联 / CLI `link` / 项目 `defaults` 与 `keys_json` /
> 翻译键三视图合一（A 定稿）/ 撤销重做。
> 前端部分（界面长什么样）另按 `AGENTS.md` 第 8 节出图定稿；这一份只写后端与数据层面的设计。

## 1. 这一批要解决什么

现在这个工具只会干一件事：打开一个 `.SC2Map` / `.SC2Mod`，处理它的翻译键。
但实际用起来，一个汉化工程里还有别的东西要看：

* 导出过的那份 `keys.json`（要能直接改，改完写回地图）；
* 地图旁边的手写笔记、说明、脚本片段（`.txt` / `.md` / `.galaxy`）；
* 参考图（`.png` / `.jpg`）；
* 以及一堆根本打不开的东西（`.dds` / `.m3` / `.ogg` / 压缩包）。

所以工程要变成一个**能看东西的工作区**，而不是只能处理一种格式的专用窗口。

## 2. 文件类型判定

打开一个文件时按下面的顺序判，**不靠扩展名**（扩展名会骗人：真的见过 `.txt` 里装压缩数据的）：

| 顺序 | 判据 | 结论 |
| --- | --- | --- |
| 1 | 扩展名是 `.SC2Map` / `.SC2Mod` | `sc2` —— 走归档解析（已有实现） |
| 2 | 前 512 字节里有 NUL，或 UTF-8 解码失败超过阈值 | `binary` —— 提示不受支持 |
| 3 | 扩展名 + 魔数命中已知图片（PNG / JPEG / GIF / WebP / BMP） | `image` —— 图片预览 |
| 4 | 其余 | `text` —— 文本编辑器 |

约定：

* **不猜编码**。UTF-8 失败就按 BOM 判 UTF-16LE / BE，再失败就当二进制。不引入 charset 猜测 —— 猜错比不猜更糟。
* **大文件挡住**：文本 > 8 MB、图片 > 64 MB 时只提示大小，不加载。打开一个 500 MB 的日志会把界面拖死。
* 类型判定与「用什么查看器」分开：先判类型，再决定渲染方式。

## 3. 翻译键下移为「项目配置」

### 3.1 现在的问题

原文语言 / 目标语言挂在**顶部标题栏**上。但语言对是**每个文件**的属性
（一个项目里 Stukov2 可能是 enUS->zhCN，另一张图是 enUS->zhTW），
放在全局标题栏上既别扭又容易误改。

### 3.2 改成什么

语言对收进**项目配置**，也就是 `.sc2translater/workspace.json` 里每个文件的条目：

```json
{
  "defaults": { "source": "enUS", "target": "zhCN" },
  "files": [
    {
      "path": "Maps/Stukov2.SC2Map",
      "source": "enUS",
      "target": "zhCN",
      "keys_json": "Maps/Stukov2.json"
    }
  ]
}
```

（`keys_json` 是关联上的同名 JSON，没有就是 null。）

* 顶部标题栏**不再放**语言对下拉；改在「项目」工具窗 / 文件右键菜单里改；
* 新加进项目的文件取 `defaults` 里的默认值；
* 改语言对只影响这一个文件；要改默认值去设置页。

### 3.3 迁移

老的 `workspace.json` 没有 `defaults` 字段时，从第一个文件的 source / target 推出来补上，
不破坏已有文件条目。

## 4. SC2 文件与同名 JSON 的关联

### 4.1 关联规则

打开 `Maps/Stukov2.SC2Map` 时，自动找**同目录同名**的 `Maps/Stukov2.json`：

| 情况 | 行为 |
| --- | --- |
| 存在且能解析成 `sc2trans.keys.v1` | 关联上，界面显示「已关联 <路径>」，写回时默认用它 |
| 存在但不是我们的格式 | 忽略，状态里说明「同名 JSON 不是翻译键格式」 |
| 不存在 | 不关联；「提取 JSON」会以 `Stukov2.json` 为默认名另存 |

**不自动创建**同名 JSON —— 在用户目录里凭空多出文件是很烦的事，必须由用户点一下。

### 4.2 四个动作

| 动作 | 语义 | 落盘 |
| --- | --- | --- |
| **提取 JSON** | 从归档导出翻译键 | 走保存对话框（默认 <同名>.json） |
| **写回归档** | 把当前 JSON 写回 map / mod | 必须选输出文件；**不覆盖输入**（已有实现的硬规矩） |
| **直接编辑** | 就在界面里改译文 | 改的是内存文档；点写回才落盘 |
| **重新关联** | 手动指定另一份 JSON | 记进 `keys_json` |

### 4.3 实现位置

关联是**纯路径推导 + 一次解析**，放在 `sc2trans-core` 里：

```rust
/// 给一份文档推导它该关联的 JSON 路径：同目录、同主文件名、扩展名 .json。
pub fn sibling_json(document: &Path) -> PathBuf;

/// 关联结果。
pub enum Link {
    Linked(PathBuf),
    ForeignSchema(PathBuf),
    Missing(PathBuf),
}
pub fn link(document: &Path) -> Link;
```

不放进 GUI —— CLI 侧同样需要（`sc2trans extract X.SC2Map` 之后
`sc2trans apply X.SC2Map X.json` 就是这条约定）。

## 5. 撤销 / 重做

### 5.1 作用范围

**每个打开的文件各自一条历史**，切文件不串味。

| 要记的操作 | 不要记的 |
| --- | --- |
| 改一条译文（连续输入合并成一步，500 ms 内的算一次） | 选中行、滚动、展开折叠 |
| 批量：原文填空译文、清空译文、导入 JSON | 切换语言对（那是配置，不是文档内容） |
| 其他键盘批量操作 | 主题 / 皮肤 / 栏宽 |

### 5.2 一处与最初设计的偏离：撤销栈放前端，不放 core

原本写的是 `crates/sc2trans-core/src/undo.rs`。实现时改了主意，理由是：

* 编辑发生在界面里，放 core 意味着**每次按键都要走一趟 IPC**；
* CLI 是非交互的，根本用不上撤销栈 —— 放 core 等于给一个用不到的地方加复杂度；
* 差分逻辑本身与领域无关，前端实现更短。

所以落在 `ui/src/composables/useHistory.ts`（10 个单测），
键仍然用 `项目 + 键 + 语言` 的稳定 id，与 core 的文档模型对得上。

### 5.3 容量与落盘

* 内存里每文件保留 **200 步**，超出丢最旧的；
* **不落盘**。关掉程序历史就没了 —— 这是刻意的：翻译键的持久化靠「写回归档」和「导出 JSON」，
  再存一份历史只会让「我改的东西到底在哪」变得难回答；
* 撤销栈存的是**差分**（改动的键 + 改前值），不是整份文档快照 ——
  一万个键的文档存 200 份快照是几百 MB。

### 5.4 交互

* `Ctrl+Z` 撤销，`Ctrl+Y` / `Ctrl+Shift+Z` 重做；
* 标题栏文件名旁显示「● 未保存」；状态栏显示可撤销步数；
* 撤销到底、重做到顶时按钮变灰，不静默失败。

## 6. 翻译键 UI：预览 or 原始文本

### 6.1 照 VS Code 处理 Markdown 的做法

VS Code 对 `.md` 是「源文件 + 可选的渲染预览」：默认编辑源文件，`Ctrl+K V` 在**旁边**开预览。
我们把关系反过来：

* **默认显示预览**（就是现在这张键表：状态 / 键 / 原文 / 译文，可直接改）；
* 右上角一个切换，随时切成**原始文本**（`key=value` 那种）；
* 两边操作的是**同一份内存文档**，随便在哪边改都行；
* 「在侧边打开原始文本」= 并排（左预览右文本）。

**定稿选了哪一种**：三版都渲染出来对比过（`scratch/preview/keys-a-inline.png` / `keys-b-side.png` / `keys-c-tabs.png`），
**选 A（单标签内切换）**。理由：中间栏通常只有 800px 上下，并排会把两边都挤扁（B 的截图里就是这个真实状态）；
三个独立标签则让标签条变成三倍长，切文件时噪音大。A 在窄栏下信息密度最高。
B 与 C 的代码已经删掉，不留三套排布。

### 6.2 为什么默认预览

汉化的人 90% 的时间在「看还剩多少、写译文」，不是在看文件格式。
但**必须**能切回原始文本 —— 有些东西（内联标记、三斜杠原文、重复键）只有在原文里才看得清。

### 6.3 三个视图的关系

| 视图 | 数据源 | 可编辑 |
| --- | --- | --- |
| 预览（键表） | 内存文档 | 是 |
| 原始文本 | 内存文档渲染成的 key=value | 是（解析回去） |
| JSON | 内存文档的 `sc2trans.keys.v1` | 是 |

三者同步是**单向渲染 + 反向解析**：谁改了就把它的内容解析回文档，再重渲染另外两个。
解析失败就地报错、**不覆盖文档**，避免把好数据冲掉。

## 8. 非目标

* **不做完整的文本编辑器**。没有语法高亮、多光标、LSP。打开文本只是「看 + 小改」。
* **不做文件管理操作**（新建 / 删除 / 重命名 / 移动）—— 那是用户的游戏目录，见工作区改造计划第 7 节。
* **不做二进制预览**（十六进制视图）。用不上，而且容易被误当成「可以改」。
* **不自动保存**。写回归档、导出 JSON 都必须用户点。

## 9. 风险

| 风险 | 缓解 |
| --- | --- |
| 类型判错（二进制当文本打开）→ 一堆乱码，甚至保存时写坏 | 按第 2 节的顺序判；**文本编辑器对非 UTF-8 内容直接拒绝保存**，只允许另存 |
| 同名 JSON 关联到别人的文件（config.json 之类） | 只认 schema 是 `sc2trans.keys.v1` 的；不是就明确说「不是翻译键格式」，不硬套 |
| 撤销栈存快照把内存吃爆 | 存差分不存快照，200 步上限 |
| 三个视图互相覆盖导致改丢 | 解析失败就地报错、不覆盖文档；写回前跑一次 `verify` |
