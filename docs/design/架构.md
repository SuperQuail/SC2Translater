# 架构

## 1. 一句话

把「MPQ 容器」和「翻译键」两件事彻底分开：容器层只认字节，领域层只认键与文本，
上层（CLI / GUI）只是两种外壳。

```
          ui/  (Vue 3 + TS)          sc2trans-cli (clap)
              |  invoke                    |
              v                            v
        src-tauri (Tauri 2 壳)  ---->  sc2trans-core
                                             |
                                             v
                                          sc2mpq
```

依赖方向不可违反；core 不知道 GUI 的存在，mpq 不知道「汉化」的存在。

## 3. 关键设计决策

### 3.1 为什么要把「字符串表」做成逐字节保真的模型

地图里的本地化文件是**玩家最终看到的东西**，任何多余改动都可能被编辑器或引擎当成异常。
所以 `StringFile` 把无法识别的行原样保留为 `Raw` 记录，只对显式修改过的键做最小改动：
BOM、换行风格、末尾换行、注释行、畸形行、甚至重复键的顺序都原样带过。
验收判据是 `verify` 里的 `string_tables_roundtrip_exact`。

### 3.2 为什么写回时要沿用原归档的布局

重建件能被银河编辑器接受，靠的不只是「格式正确」：

* `dwRawChunkSize` 必须写 0（暴雪原件写的 16384 会打开一条 MD5 校验路径）；
* BET 的 `unknown08` 沿用原件（实测恒为 7888，StormLib 写的是 0x10）；
* 每个组件的分块方式（SINGLE_UNIT / 分扇区）沿用原件；
* 组件集合没变时沿用原件的 `(listfile)`，做到「无改动则逐字节复现」。

这些都在 `sc2mpq::Document` 打开时快照、保存时回填。

### 3.3 经典哈希表的空槽（本项目发现并修掉的一个真 bug）

读取器判定「加密的哈希表是否有效」时会要求**至少有一个空闲槽**。
当组件数恰好是 2 的幂时，表会被填满，于是添加一个新组件后连 `(listfile)` 都读不出来。
修法：保存前按「至少留一个空槽、负载不超过 7/8」重新算表大小，且只在需要时才放大。
（`crates/sc2mpq/src/archive.rs` 的 `Document::save`，有专门的回归测试）

### 3.4 为什么 CLI 面向 agent、GUI 面向人

* CLI：**stdout 只有结果**（`--json` 时是一个 JSON 对象），进度与告警走 stderr，
  退出码 0/1；`--json` 放在子命令前后都认。
* GUI：三栏工作面（概览与过滤 / 键表 / 详情），所有重活走 `spawn_blocking`。
* 两者共用 `sc2trans-core`，所以行为不可能漂。

### 3.5 为什么删掉了 Python 原型

调研期确实有一份 Python 对照实现：事实先用它逐字节钉死，Rust 侧再实现，
最后两边做差分测试（同图 677/677 逐字段一致、产物组件逐字节相同）。

调研结束后它就被删了。理由很直接：那些事实已经落到两处更可靠的地方 ——
`docs/research/*.md` 记着结论与证据，`cargo test` 在 5 个真实归档上逐字节断言。
而留着一份并行实现的实际代价是**每次改 JSON 契约要同步三处**，
换来的是「可以再跑一次差分」这个几乎不会用到的能力。

## 4. 数据流

### extract

```
Archive::open            只解析表 + 读 listfile（不碰业务组件）
  -> locale_tables()     扫出所有 <locale>.SC2Data/LocalizedData/*.txt
  -> StringFile::parse   解析成 键/值/原文 三元组
  -> 以 source_locale 为原文、target_locale 为对照，算 status
  -> TranslationDocument 序列化成 sc2trans.keys.v1
```

### apply / seed

```
normalize_input  接受完整结构，也接受手写扁平 {key: value}
  -> 按 file 分组，取 target（空则按需回落 source）
  -> Document::open   读入全部组件（含簿记项）
  -> StringFile       目标语言的表；不存在就用源语言文件的 BOM/换行做模板新建
  -> Document::save   重算 (listfile)/(attributes)/HET/BET/头部摘要，写盘
  -> 回读校验         重新打开产物，确认每个键都读得回来
```

## 6. 已知的技术债

| 项 | 说明 |
| --- | --- |
| `SECTOR_CRC` 块的尾部 dword 语义未知 | 读取不受影响（`offsets[0]` 已把它算进去），写入从不产出 SECTOR_CRC |
| BET `unknown08` 语义未知 | 只能沿用原件值；从零构建归档时会写 0x10，尚未做受控 A/B |
| HET `totalCount` 公式 | `entryCount*4/3` 对某个真实样本不成立（17→实测 23）；读取用磁盘值，写入自洽即可 |
| 读取走经典哈希表 | 引擎优先走 HET；两者在 5 个真实样本上逐名一致，但「按引擎行为读」尚未验证 |
| 未做编辑器/游戏内实机验收 | 需要人工，见 `验收清单.md` |
